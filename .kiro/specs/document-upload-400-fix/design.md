# Document Upload 400 Fix Bugfix Design

## Overview

Uploading a document from the Documents page fails with HTTP 400 Bad Request. The shared axios client in `frontend/src/services/api.ts` is created with a hard-coded default header `Content-Type: application/json`. This default is applied to every outgoing request, including the multipart `FormData` upload sent by `documentService.uploadDocument`. Because the header is pinned to `application/json`, the browser never gets the chance to set the correct `multipart/form-data; boundary=...` content type, so the backend (`POST /api/documents/upload`, which declares `file: UploadFile = File(...)` and `access_level: AccessLevel = Form(...)`) cannot parse the body and rejects the request.

The fix is a request interceptor in the shared axios client that detects when the request body is a `FormData` instance and removes the forced `Content-Type` header. When axios/the browser sees no explicit content type on a `FormData` body, it generates the correct `multipart/form-data` content type with a boundary. All other requests — JSON bodies, the `Authorization` header, and the 401 redirect behavior — remain untouched.

## Glossary

- **Bug_Condition (C)**: The condition that triggers the bug — an outgoing request whose body is `FormData` while the client forces `Content-Type: application/json`, dropping the multipart boundary.
- **Property (P)**: The desired behavior — `FormData` uploads are sent with a browser-generated `multipart/form-data` content type (including a boundary), never `application/json`.
- **Preservation**: Existing behavior that must remain unchanged — JSON requests keep `Content-Type: application/json`, the `Authorization: Bearer <token>` header keeps being attached, and the 401-on-protected-endpoint redirect keeps working.
- **api (axios client)**: The shared axios instance in `frontend/src/services/api.ts` used by all frontend services.
- **FormData**: A browser multipart body type. When it is the request body and no explicit `Content-Type` is set, the browser derives `multipart/form-data; boundary=...`.
- **config.data**: The axios request config field holding the request body; it is a `FormData` instance for the upload path.

## Bug Details

### Bug Condition

The bug manifests when an outgoing request carries a `FormData` body but the shared axios client forces `Content-Type: application/json`. The client either applies its hard-coded default JSON content type to the multipart body, or otherwise fails to let the browser generate the `multipart/form-data` boundary, so the backend receives an unparseable multipart request.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type OutgoingRequest
  OUTPUT: boolean

  RETURN isFormData(input.data)
         AND input.headers["Content-Type"] = "application/json"
END FUNCTION
```

### Examples

- Admin uploads `report.pdf` via the Documents page. Expected: request sent as `multipart/form-data; boundary=...`, backend responds `201 Created`. Actual: request sent as `application/json`, backend responds `400 Bad Request`, no document created.
- `documentService.uploadDocument(file, 'private')` builds a `FormData` with `file` and `access_level`. Expected: browser sets multipart content type. Actual: content type pinned to `application/json`, multipart boundary missing.
- A JSON login request (`POST /auth/login`) with a plain object body. Expected and actual: sent as `application/json` — this input does NOT satisfy the bug condition and must stay unchanged.
- Edge case: a `FormData` body with no explicit per-request `Content-Type` override. Expected: content type generated by the browser as `multipart/form-data` with a boundary.

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- JSON request bodies (login, forum, and other `POST`/`PUT` calls) must continue to be sent with `Content-Type: application/json`.
- The `Authorization: Bearer <token>` header must continue to be attached when an access token is present.
- A 401 on a non-auth (protected) endpoint must continue to clear the stored token and redirect to `/login`, while 401s on `/auth/login` and `/auth/login/2fa` continue to be surfaced to the caller.
- Backend authorization and validation behavior is unchanged: non-admin uploads are still rejected, and unsupported file extensions still return the 400 "unsupported category" error.

**Scope:**
All inputs that do NOT involve a `FormData` body under a forced JSON content type should be completely unaffected by this fix. This includes:
- JSON request bodies for any endpoint.
- The request interceptor logic that attaches the `Authorization` header.
- The response interceptor logic that handles 401 redirects and the auth-endpoint exception list.

## Hypothesized Root Cause

Based on the bug description and the code in `frontend/src/services/api.ts`, the most likely issues are:

1. **Hard-coded default JSON content type (primary)**: The axios instance is created with `headers: { 'Content-Type': 'application/json' }`. This default is merged into every request config, including `FormData` uploads, so the browser never sets the multipart boundary.
   - The upload path is `documentService.uploadDocument` → `api.post('/documents/upload', form)` where `form` is a `FormData`.
   - The backend router declares `file: UploadFile = File(...)` and `access_level: AccessLevel = Form(...)`, which require a multipart body with a boundary.

2. **No FormData-aware content-type handling**: There is no request interceptor logic that detects `config.data instanceof FormData` and strips the forced content type, so the JSON default always wins.

3. **Content type set at instance level rather than per-request**: Because the JSON content type lives in the instance defaults, individual callers would each have to remember to override it; a centralized interceptor is the robust fix.

## Correctness Properties

Property 1: Bug Condition - FormData uploads use multipart content type

_For any_ request where the bug condition holds (isBugCondition returns true — the body is `FormData`), the fixed client SHALL send the request with a `Content-Type` that starts with `multipart/form-data` (browser-generated, including a boundary) and SHALL NOT send `Content-Type: application/json`, so the backend can parse the `file` and `access_level` fields and respond `201 Created`.

**Validates: Requirements 2.1, 2.2**

Property 2: Preservation - Non-FormData requests are unchanged

_For any_ request where the bug condition does NOT hold (isBugCondition returns false — a JSON or non-FormData body), the fixed client SHALL produce the same result as the original client, preserving the `application/json` content type on JSON requests, the `Authorization: Bearer <token>` header, and the 401 clear-token-and-redirect behavior on protected endpoints.

**Validates: Requirements 3.1, 3.2, 3.3**

## Fix Implementation

### Changes Required

Assuming our root cause analysis is correct:

**File**: `frontend/src/services/api.ts`

**Function**: the request interceptor (`api.interceptors.request.use`)

**Specific Changes**:
1. **Detect FormData bodies**: In the existing request interceptor, after (or alongside) attaching the `Authorization` header, check `config.data instanceof FormData`.
   - When true, delete the forced content type so the browser can set `multipart/form-data` with a boundary.

2. **Remove the forced Content-Type for FormData**: When the body is `FormData`, `delete config.headers['Content-Type']` (and defensively remove the lowercase `content-type` variant if present), leaving axios to omit the header so the browser generates it.

3. **Leave JSON requests untouched**: Do not modify headers for non-FormData bodies; the instance default `Content-Type: application/json` continues to apply.

4. **Preserve the Authorization header logic**: The token-attaching branch stays exactly as it is; the FormData check must not interfere with attaching `Authorization`.

5. **Preserve the response interceptor**: No changes to the 401 handling, the `AUTH_ENDPOINTS` list, or `isAuthEndpoint`; the fix is confined to the request interceptor's content-type handling.

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed code, then verify the fix works correctly and preserves existing behavior.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm or refute the root cause analysis. If we refute, we will need to re-hypothesize.

**Test Plan**: Write tests that run the request interceptor against a config whose `data` is a `FormData` instance, and assert on the resulting `Content-Type` header. Run these tests on the UNFIXED interceptor to observe that the JSON content type is retained.

**Test Cases**:
1. **FormData upload content type**: Pass a config with `data` = `FormData` and default `Content-Type: application/json`; assert the resulting header is not `application/json` (will fail on unfixed code).
2. **Upload endpoint integration**: Simulate `documentService.uploadDocument(file)` and assert the outgoing request would carry a multipart content type (will fail on unfixed code).
3. **Boundary presence**: Assert that once the JSON content type is removed, no explicit `Content-Type` remains so the browser can add the boundary (will fail on unfixed code).
4. **Out-of-scope JSON control**: Pass a config with a plain-object JSON body and assert `Content-Type: application/json` is retained (should pass on unfixed code — used to confirm scope).

**Expected Counterexamples**:
- The `Content-Type` header remains `application/json` for a `FormData` body.
- Possible causes: hard-coded instance default content type, no FormData-aware interceptor, per-request override missing.

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds, the fixed function produces the expected behavior.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := requestInterceptor_fixed(input)
  ASSERT result.headers["Content-Type"] != "application/json"
      AND (result.headers has no explicit "Content-Type"
           OR contentTypeOf(result) STARTS_WITH "multipart/form-data")
END FOR
```

### Preservation Checking

**Goal**: Verify that for all inputs where the bug condition does NOT hold, the fixed function produces the same result as the original function.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT requestInterceptor_original(input) = requestInterceptor_fixed(input)
END FOR
```

**Testing Approach**: Property-based testing is recommended for preservation checking because:
- It generates many test cases automatically across the input domain.
- It catches edge cases that manual unit tests might miss.
- It provides strong guarantees that behavior is unchanged for all non-buggy inputs.

**Test Plan**: Observe behavior on UNFIXED code first for JSON bodies, the Authorization header, and 401 handling, then write property-based tests capturing that behavior so it is verified after the fix.

**Test Cases**:
1. **JSON content type preservation**: Observe that JSON bodies keep `application/json` on unfixed code, then write a test to verify this continues after the fix.
2. **Authorization header preservation**: Observe that the `Authorization: Bearer <token>` header is attached when a token is present on unfixed code, then write a test to verify this continues after the fix.
3. **401 redirect preservation**: Observe that a 401 on a protected endpoint clears the token and redirects to `/login`, and that `/auth/login` 401s do not, on unfixed code, then write tests to verify both continue after the fix.

### Unit Tests

- Test that the request interceptor removes the forced `Content-Type` when `config.data` is a `FormData` instance.
- Test that the request interceptor leaves `Content-Type: application/json` unchanged for plain-object/JSON bodies.
- Test that the `Authorization` header is still attached when a token is present, for both FormData and JSON bodies.

### Property-Based Tests

- Generate random non-FormData request configs (varied URLs, methods, header presence) and verify the interceptor output is identical to the original for content type and Authorization handling (preservation).
- Generate random FormData bodies and verify the resulting content type is never `application/json` (fix checking).
- Generate random token/no-token states and verify the Authorization header behavior is unchanged across FormData and JSON requests.

### Integration Tests

- Test the full upload flow: admin uploads a supported file and the Documents page clears the error and refreshes the list showing the new document (201 path).
- Test that a non-admin upload is still rejected with an authorization error and no document is created.
- Test that an admin upload of an unsupported extension still returns the 400 "unsupported category" error and no document is created.
