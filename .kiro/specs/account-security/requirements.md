# Requirements Document

## Introduction

This feature adds an account security management capability to the web interface. Authenticated users gain access to a dedicated, protected page at `/account/security` (French UI) reached from a user/gear icon in the application header. From this page a user can change their password, trigger a password-reset email to their own registered address, and enable or disable two-factor authentication (2FA) using either a TOTP authenticator application or an email verification code. When 2FA is enabled, the login flow requires a second verification step. The feature spans the React/TypeScript frontend and the FastAPI backend, including new authenticated endpoints, new User model fields for 2FA, an Alembic migration, and integration with the existing password-reset email flow and audit logging.

## Glossary

- **Account_Security_Page**: The protected frontend page rendered at the route `/account/security` that presents password and two-factor authentication management controls.
- **Header_Security_Link**: The user/gear icon control placed in the application header next to the "Déconnexion" button that navigates to the Account_Security_Page.
- **Auth_Backend**: The FastAPI authentication service exposing endpoints under `/api/auth/*`.
- **Change_Password_Endpoint**: A new authenticated backend endpoint that changes the password of the currently authenticated user after verifying the current password.
- **Password_Reset_Flow**: The existing email-based password-reset mechanism exposed by `requestPasswordReset`/`resetPassword` and backed by the Auth_Backend email service.
- **TOTP_2FA**: Two-factor authentication using a time-based one-time password generated by an authenticator application (for example Google Authenticator, Authy, or Microsoft Authenticator), implemented server-side with the pyotp library.
- **Email_2FA**: Two-factor authentication that delivers a verification code to the user's registered email address at each login.
- **TwoFactor_Status_Endpoint**: A backend endpoint that returns the current 2FA configuration state for the authenticated user.
- **Login_Flow**: The authentication sequence that validates credentials and, when 2FA is enabled, requires a second verification step before issuing a session token.
- **Audit_Log**: The existing backend audit logging facility that records security-relevant actions.
- **Current_User**: The authenticated user resolved by the backend `get_current_user` dependency.

## Requirements

### Requirement 1: Header access point

**User Story:** As an authenticated user, I want a security link in the header, so that I can reach my account security settings from any page.

#### Acceptance Criteria

1. WHERE the user is authenticated, THE Header_Security_Link SHALL be displayed as an icon-only control positioned next to the "Déconnexion" button in the desktop header.
2. WHERE the user is authenticated AND the mobile menu is displayed, THE Header_Security_Link SHALL be displayed as a labeled entry in the mobile menu.
3. THE Header_Security_Link SHALL use white-on-blue styling consistent with the existing header controls in Layout.tsx.
4. WHEN the user activates the Header_Security_Link, THE Header_Security_Link SHALL navigate the browser to the route `/account/security`.

### Requirement 2: Protected security page

**User Story:** As an authenticated user, I want a dedicated security page, so that I can manage my password and two-factor settings in one place.

#### Acceptance Criteria

1. THE Account_Security_Page SHALL be registered at the route `/account/security`.
2. WHERE a request targets the route `/account/security` from an unauthenticated session, THE Account_Security_Page SHALL redirect the request to the login route.
3. THE Account_Security_Page SHALL present all user-facing text in French.
4. THE Account_Security_Page SHALL display a password management section and a two-factor authentication section.

### Requirement 3: Change password

**User Story:** As an authenticated user, I want to change my password by providing my current and new password, so that I can update my credentials securely.

#### Acceptance Criteria

1. THE Account_Security_Page SHALL provide input fields for the current password and the new password.
2. WHEN the user submits a password change, THE Account_Security_Page SHALL send the current password and the new password to the Change_Password_Endpoint over an authenticated request.
3. WHEN the Change_Password_Endpoint receives a request, THE Change_Password_Endpoint SHALL verify that the submitted current password matches the stored credential of the Current_User before applying any change.
4. WHEN the current password is verified and the new password is accepted, THE Change_Password_Endpoint SHALL persist the new password as the credential of the Current_User.
5. IF the submitted current password does not match the stored credential, THEN THE Change_Password_Endpoint SHALL reject the request and return an authentication error without changing the stored credential.
6. WHEN a password change is applied, THE Change_Password_Endpoint SHALL record the event in the Audit_Log.
7. WHEN the Change_Password_Endpoint returns a result, THE Account_Security_Page SHALL display a French confirmation message on success and a French error message on failure.

### Requirement 4: Reset password by email

**User Story:** As an authenticated user, I want to reset my password by email, so that I can recover access using the standard email flow for my own address.

#### Acceptance Criteria

1. THE Account_Security_Page SHALL provide a "Réinitialiser par Email" control.
2. WHEN the user activates the "Réinitialiser par Email" control, THE Account_Security_Page SHALL invoke the Password_Reset_Flow for the registered email address of the Current_User.
3. WHEN the Password_Reset_Flow is invoked for the Current_User, THE Auth_Backend SHALL send a password-reset email to the registered email address of the Current_User.
4. WHEN the Password_Reset_Flow completes, THE Account_Security_Page SHALL display a French confirmation message indicating that a reset email was sent.

### Requirement 5: TOTP authenticator two-factor setup

**User Story:** As an authenticated user, I want to set up an authenticator app for two-factor authentication, so that I can protect my account with time-based codes.

#### Acceptance Criteria

1. WHEN the user begins TOTP_2FA setup, THE Auth_Backend SHALL generate a TOTP secret for the Current_User and return a QR-code-compatible provisioning value and the secret using pyotp.
2. WHILE TOTP_2FA setup is pending, THE Account_Security_Page SHALL display the QR code and the secret for the user to register in an authenticator application.
3. WHEN the user submits a TOTP code to confirm setup, THE Auth_Backend SHALL validate the submitted code against the generated secret before enabling TOTP_2FA.
4. WHEN a submitted TOTP confirmation code is valid, THE Auth_Backend SHALL enable TOTP_2FA for the Current_User and persist the associated 2FA fields on the User record.
5. IF a submitted TOTP confirmation code is invalid, THEN THE Auth_Backend SHALL reject the request and leave TOTP_2FA disabled for the Current_User.
6. THE User data model SHALL include fields that store the TOTP secret and the enabled state of TOTP_2FA, provisioned through an Alembic migration.

### Requirement 6: Email two-factor setup

**User Story:** As an authenticated user, I want to enable email-based two-factor authentication, so that I receive a verification code by email at each login.

#### Acceptance Criteria

1. WHEN the user enables Email_2FA, THE Auth_Backend SHALL enable Email_2FA for the Current_User and persist the associated 2FA field on the User record.
2. THE User data model SHALL include a field that stores the enabled state of Email_2FA, provisioned through an Alembic migration.

### Requirement 7: Two-factor enforcement during login

**User Story:** As a user with two-factor authentication enabled, I want the login to require a second verification step, so that a stolen password alone cannot access my account.

#### Acceptance Criteria

1. WHERE TOTP_2FA is enabled for the user AND primary credentials are validated, THE Login_Flow SHALL require a valid TOTP code before issuing a session token.
2. WHERE Email_2FA is enabled for the user AND primary credentials are validated, THE Login_Flow SHALL send a verification code to the user's registered email address and require a matching code before issuing a session token.
3. IF the second verification step receives an invalid code, THEN THE Login_Flow SHALL reject the login attempt and return a verification error without issuing a session token.
4. WHERE no 2FA method is enabled for the user AND primary credentials are validated, THE Login_Flow SHALL issue a session token without a second verification step.

### Requirement 8: Two-factor status display

**User Story:** As an authenticated user, I want to see my current two-factor status, so that I know which protection methods are active.

#### Acceptance Criteria

1. WHEN the Account_Security_Page loads, THE Account_Security_Page SHALL request the current 2FA configuration from the TwoFactor_Status_Endpoint.
2. WHEN the TwoFactor_Status_Endpoint returns a result, THE Account_Security_Page SHALL display the enabled state of TOTP_2FA and Email_2FA in French.
3. IF the request to the TwoFactor_Status_Endpoint fails, THEN THE Account_Security_Page SHALL display a French error message indicating that the 2FA status could not be loaded.
