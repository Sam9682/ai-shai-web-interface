# Requirements Document

## Introduction

This feature adds a new "OPCP Context" tab as the first entry in the prerequisites checklist tabs, placed before the existing Network Checklist, Core Control Plane, CloudStore, VCF, and Servers tabs. Unlike existing question/answer and servers tabs, this tab presents a labeled key/value information form organized into sections and subsections that capture OPCP installation context (client environment, contacts, and use cases).

The tab introduces a new tab kind (`context`) with its own form component and render branch. Its field values are editable per installation and seeded with defaults when no stored value exists. Editing is restricted to administrators; members and other non-administrators view the tab in read-only mode. The context values participate in export/import round-trips and are rendered into the generated architecture document. Existing tabs retain their current authentication-based gating unchanged.

## Glossary

- **OPCP_Context_Tab**: The new prerequisites checklist tab, identified by a new tab `kind` value `context`, that displays OPCP installation context as labeled key/value rows grouped into sections and subsections.
- **Checklist_Tab_System**: The component responsible for ordering and rendering the prerequisites checklist tabs, defined by `CHECKLIST_CATEGORIES` in `checklistCategories.ts` and rendered by `ChecklistTabs.tsx`.
- **Context_Form**: The new form component that renders the OPCP_Context_Tab labeled key/value rows, mirroring the read-only/disabled and styling patterns of `QuestionAnswerForm`.
- **Context_Config**: The configuration shape describing the OPCP_Context_Tab, consisting of ordered sections, optional nested subsections, and labeled key/value rows where each row has an `id`, a `label`, and a `defaultValue`.
- **Context_Row**: A single labeled key/value entry within the Context_Config, identified by a unique `rowId`.
- **Persistence_Service**: The `prerequisitesService` providing `loadClientAnswers(installationId, slug)` and `saveClientAnswer(installationId, slug, rowId, value)`, backed by a flat `rowId → value` store keyed by `(installationId, slug, rowId)`.
- **Auth_Service**: The `authService` providing `isAdmin()` (true when the stored `user_role` is `administrator`) and `isAuthenticated()`.
- **Administrator**: A user for whom `Auth_Service.isAdmin()` returns `true`.
- **Non_Administrator**: A user for whom `Auth_Service.isAdmin()` returns `false`, including members and unauthenticated viewers.
- **Export_Service**: The `installationExport.ts` module that produces export JSON, consumes import JSON, clears installation values, and builds the architecture document HTML via `buildArchitectureDocumentHtml`.
- **Architecture_Document**: The HTML document generated by `buildArchitectureDocumentHtml`.
- **Installation**: A single OPCP installation record identified by an `installationId`, against which context values are stored.

## Requirements

### Requirement 1

**User Story:** As a user of the prerequisites checklist, I want the OPCP Context tab to appear first, so that I review installation context before the other checklists.

#### Acceptance Criteria

1. THE Checklist_Tab_System SHALL include the OPCP_Context_Tab as the first entry of `CHECKLIST_CATEGORIES`, positioned before the Network Checklist, Core Control Plane, CloudStore, VCF, and Servers tabs.
2. THE OPCP_Context_Tab SHALL use a tab `kind` value of `context`.
3. WHEN the Checklist_Tab_System renders the tab list, THE Checklist_Tab_System SHALL display the OPCP_Context_Tab title ahead of all other tab titles.
4. WHERE a tab has `kind` value `context`, THE Checklist_Tab_System SHALL render that tab using the Context_Form.

### Requirement 2

**User Story:** As a user, I want the OPCP Context tab to show all sections, subsections, and rows, so that I can view the complete installation context.

#### Acceptance Criteria

1. THE Context_Form SHALL render each section defined in the Context_Config in the configured order.
2. THE Context_Form SHALL render the "Client Environnement" section containing the rows "Nom du client", "Type de deploiement", "Site 1 Location", "Site 2 Location", "Installation wish date", and "Managed / Air-gapped".
3. THE Context_Form SHALL render the "Contacts" section containing the subsection "OVH PSMC Architecte" with rows "Nom", "Téléphone", and "Email".
4. THE Context_Form SHALL render the "Contacts" section containing the subsection "Client : MDC MAROC" with rows "Nom", "Téléphone", and "Email".
5. THE Context_Form SHALL render the "Use cases (?)" section containing the rows "VCF", "SUSE Harvester", "Nutanix", "IA", and "Kubernetes".
6. WHERE a section defines nested subsections, THE Context_Form SHALL render each subsection heading above its labeled key/value rows.
7. THE Context_Form SHALL render each Context_Row as a free-text input field paired with the row label.
8. THE Context_Form SHALL render each row label using French localized strings obtained via `useTranslation`.

### Requirement 3

**User Story:** As a viewer, I want unset context rows to display their seeded defaults, so that the tab shows meaningful starting values before anyone edits them.

#### Acceptance Criteria

1. WHEN the Context_Form loads a Context_Row for which no saved value exists for the current Installation, THE Context_Form SHALL display the row `defaultValue`.
2. WHEN the Context_Form loads a Context_Row for which a saved value exists for the current Installation, THE Context_Form SHALL display the saved value.
3. THE Context_Form SHALL seed the "Client Environnement" section defaults as "Nom du client"=`MDC MAROC`, "Type de deploiement"=`NanoPod`, "Site 1 Location"=`« Demo » MDC Rabat`, "Site 2 Location"=empty, "Installation wish date"=empty, and "Managed / Air-gapped"=`Managed`.
4. THE Context_Form SHALL seed the "OVH PSMC Architecte" subsection defaults as "Nom"=`Samuel LEPETRE`, "Téléphone"=empty, and "Email"=`samuel.lepetre@ovhcloud.com`.
5. THE Context_Form SHALL seed the "Client : MDC MAROC" subsection defaults as "Nom"=empty, "Téléphone"=empty, and "Email"=empty.
6. THE Context_Form SHALL seed the "Use cases (?)" section defaults as "VCF"=`Within Scope`, "SUSE Harvester"=`Out of Scope`, "Nutanix"=`Out of Scope`, "IA"=`Out of Scope`, and "Kubernetes"=`Out of Scope`.

### Requirement 4

**User Story:** As an administrator, I want to edit context rows and have changes persist per installation, so that the recorded context reflects the specific deployment.

#### Acceptance Criteria

1. WHILE the current user is an Administrator, THE Context_Form SHALL render each Context_Row input as editable.
2. WHEN an Administrator changes a Context_Row value, THE Context_Form SHALL call `Persistence_Service.saveClientAnswer(installationId, slug, rowId, value)` with the current Installation identifier, the OPCP_Context_Tab slug, the row identifier, and the new value.
3. WHEN the Context_Form reloads for an Installation after an Administrator has saved a Context_Row value, THE Context_Form SHALL display the previously saved value for that row.
4. THE Context_Form SHALL persist a Context_Row value only when that row is edited, keeping unedited rows as default-seeded without stored values.

### Requirement 5

**User Story:** As a non-administrator, I want the OPCP Context tab to be read-only, so that I can view context without changing it.

#### Acceptance Criteria

1. WHILE the current user is a Non_Administrator, THE Context_Form SHALL render each Context_Row input as read-only and disabled, mirroring the `QuestionAnswerForm` read-only pattern.
2. WHILE the current user is a Non_Administrator, THE Context_Form SHALL apply the read-only field styling consistent with `READONLY_FIELD_CLASS`.
3. WHILE the current user is a Non_Administrator, THE Context_Form SHALL omit calls to `Persistence_Service.saveClientAnswer` for Context_Row values.
4. THE Context_Form SHALL determine editability using `Auth_Service.isAdmin()`.

### Requirement 6

**User Story:** As a user managing installations, I want context values included in export and import, so that I can transfer a complete installation between environments.

#### Acceptance Criteria

1. WHEN the Export_Service produces export JSON for an Installation, THE Export_Service SHALL include the OPCP_Context_Tab values in the export tabs map keyed by the OPCP_Context_Tab slug.
2. WHEN the Export_Service imports JSON containing OPCP_Context_Tab values, THE Export_Service SHALL restore each Context_Row value whose identifier matches a valid Context_Row identifier for the current Installation.
3. IF imported JSON contains a row identifier that does not match a valid Context_Row identifier, THEN THE Export_Service SHALL skip that identifier without restoring a value.
4. WHEN export JSON is produced for an Installation and then imported into an Installation, THE Export_Service SHALL reproduce the same OPCP_Context_Tab row values that were exported.
5. WHEN the Export_Service clears installation values, THE Export_Service SHALL include the OPCP_Context_Tab row values among the cleared values.

### Requirement 7

**User Story:** As a user generating documentation, I want context values rendered in the architecture document, so that the document reflects the installation context.

#### Acceptance Criteria

1. WHEN `buildArchitectureDocumentHtml` generates the Architecture_Document, THE Export_Service SHALL include the OPCP_Context_Tab title in the document table of contents.
2. WHEN `buildArchitectureDocumentHtml` generates the Architecture_Document, THE Export_Service SHALL render a section containing the OPCP_Context_Tab labeled key/value rows grouped by their sections and subsections.
3. WHEN a Context_Row has no saved value for the Installation, THE Export_Service SHALL render the row `defaultValue` in the Architecture_Document.
4. WHEN a Context_Row has a saved value for the Installation, THE Export_Service SHALL render the saved value in the Architecture_Document.

### Requirement 8

**User Story:** As a maintainer, I want existing tabs' behavior unchanged, so that adding the OPCP Context tab does not regress current functionality.

#### Acceptance Criteria

1. THE Checklist_Tab_System SHALL retain the existing `isAuthenticated()`-based gating for all tabs with `kind` value `qa` and `servers`.
2. THE OPCP_Context_Tab SHALL be the only tab whose edit gating uses `Auth_Service.isAdmin()`.
3. THE Export_Service SHALL continue to render the existing servers section for tabs with `kind` value `servers` without modification to that behavior.
4. THE Checklist_Tab_System SHALL preserve the existing relative order of the Network Checklist, Core Control Plane, CloudStore, VCF, and Servers tabs after inserting the OPCP_Context_Tab first.
